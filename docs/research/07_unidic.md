# UniDic調査レポート

## 1. 概要と特徴

### UniDicとは

UniDic（ユニディック）は、国立国語研究所（NINJAL）が開発した形態素解析器MeCab用の電子化辞書である。正式名称は「国語研短単位自動解析用辞書」。国語研が規定した**斉一な言語単位（短単位）**に基づき設計されており、表記の揺れや語形の変異にかかわらず一貫した解析結果を返すことを特徴とする。

### 設計思想

UniDicの設計は以下の3つの原則に基づく：

1. **短単位による斉一性**: 文脈の有無や違いによらず、一貫した自動解析を実現
2. **可能性に基づく品詞体系**: 用法による品詞の区別を行わず、当該短単位がとり得る用法をすべて考慮した1つの品詞を付与
3. **語源主義に基づく脱文脈化**: 語源に基づいて同一と見なしうる語に対して同一の見出しを付与

### 階層的見出し構造

UniDicの最大の特徴は、4段階の階層的見出し構造を持つことである：

```
語彙素（Lemma）
├── 語形（Word Form）
│   ├── 書字形（Orthographic Form）
│   │   ├── 出現形（Surface Form）
│   │   └── 基本形（Base Form）
│   └── 発音形（Pronunciation Form）
│       ├── 出現形
│       └── 基本形
```

| 階層 | 説明 | 例 |
|------|------|-----|
| **語彙素** | 国語辞典の見出しに相当する最上位層。語形の変異や表記の揺れを超えて同一語に同一の見出しを与える | 「大きい」 |
| **語形** | 同一語彙素に属する語形の変異を区別 | 矢張り -> {ヤハリ, ヤッパリ, ヤッパ} |
| **書字形** | 同一語形に属する表記の揺れを区別 | ヤハリ -> {やはり, ヤハリ, 矢張り} |
| **発音形** | 同一語形の発音の違いを区別 | データ -> {データ, データー} |

### IPADICとの主な違い

| 比較項目 | IPADIC | UniDic |
|---------|--------|--------|
| 開発元 | IPA（情報処理推進機構） | NINJAL（国立国語研究所） |
| 単位 | 独自の単位（長め） | 短単位（短め、斉一） |
| 品詞体系 | IPA品詞体系 | 可能性に基づく品詞体系（より詳細） |
| 形容動詞 | 「名詞-形容動詞語幹」として扱う | 「形状詞」という独自品詞を導入 |
| 見出し構造 | フラット | 語彙素-語形-書字形-発音形の階層構造 |
| アクセント情報 | なし | あり（aType, aConType, aModType） |
| 語種情報 | なし | あり（和語/漢語/外来語/混種語等） |
| 語頭・語末変化 | なし | あり（iType, iForm, fType, fForm） |
| フィールド数 | 9フィールド | 29フィールド |
| 辞書サイズ | 小さい | 大きい（約133MB） |

### 読み情報の違い

| 項目 | IPADIC | UniDic |
|------|--------|--------|
| 読み表記 | readingフィールド（1つ） | lForm, pron, pronBase, kana, kanaBase（複数） |
| 長音表記 | カタカナのみ | 長音をーで表記（pron）、カタカナ表記（kana） |
| 語形変異 | 区別なし | 語形レベルで区別 |
| 発音情報 | 発音フィールド（1つ） | 出現形と基本形を分離 |

### アクセント情報の違い

| 項目 | IPADIC | UniDic |
|------|--------|--------|
| アクセント型 | なし | aType（アクセント核位置） |
| 結合型 | なし | aConType（複合語アクセント） |
| 修飾型 | なし | aModType（アクセント修飾） |

### NAIST-jdicとの関係

NAIST-jdicはIPADICの後継辞書であり、IPADICの全エントリをチェックして品詞整理・表記ゆれ情報付与・複合語構造付与を行ったものである。OpenJTalkで使用されるmecab-naist-jdicは、NAIST-jdicの情報にアクセント関連フィールドを2つ追加拡張（フィールド14: アクセント核位置/モーラ数、フィールド15: アクセント結合タイプ）したフォーマットを採用している。

## 4. UniDicのバリエーション

### 主要バリエーション

| 名称 | 略称 | 対象 | 説明 |
|------|------|------|------|
| **現代書き言葉UniDic** | CWJ | 書き言葉 | 書籍・雑誌・新聞等の現代書き言葉テキスト解析用。BCCWJの解析に使用 |
| **現代話し言葉UniDic** | CSJ | 話し言葉 | 日本語話し言葉コーパス（CSJ）に基づく。日常会話・講演等の解析用 |
| **古文用UniDic** | CHJ | 古典文語 | 日本語歴史コーパス（CHJ）用。古典日本語テキストの解析 |

### 各バリエーションの特徴

#### UniDic-cwj（現代書き言葉）
- **ベースコーパス**: 現代日本語書き言葉均衡コーパス（BCCWJ）
- **用途**: 新聞記事、書籍、ウェブテキスト等の解析
- **語彙規模**: 最も大きい
- **一般的なG2P用途に最適**

#### UniDic-csj（現代話し言葉）
- **ベースコーパス**: 日本語話し言葉コーパス（CSJ）
- **用途**: 音声認識結果のテキスト、講演録、会話テキストの解析
- **特徴**: 話し言葉特有の表現・縮約形に対応
- **歴史**: UniDicの原型はCSJの解析用に作られた

#### UniDic-lite
- **概要**: unidic-pyパッケージで提供される軽量版
- **特徴**: フィールドのサブセットのみ含む（全29フィールドではない）
- **用途**: Python環境での軽量な形態素解析

### 最新バージョン

2025年12月時点の最新版は **202512** である（CWJ/CSJ共通バージョン番号）。

## 5. アクセント情報の詳細

### UniDicに含まれるアクセント情報

UniDicは辞書内にアクセント情報を含んでおり、これはIPADICやNAIST-jdic（拡張前）にはない大きな特徴である。

#### アクセント型（aType）

- **定義**: 標準語（東京方言）におけるアクセント核の位置をモーラ番号で表す
- **値の例**:
  - `0` = 平板型（アクセント核なし）
  - `1` = 頭高型（1モーラ目にアクセント核）
  - `2` = 中高型（2モーラ目にアクセント核）
  - `3` = 尾高型/中高型（3モーラ目にアクセント核）
- **複数値**: カンマ区切りで複数のアクセント型を持つ場合がある（頻度の高い順）
  - 例: `0,3` = 平板型が主で、3モーラ目核型も許容

#### アクセント結合型（aConType）

- **定義**: 複合語を形成する際のアクセント変化規則を示す
- **用途**: 複合語のアクセント核位置の計算に使用
- **記法**: 複雑な記法で表現され、助数詞表現等でのアクセント変化を記述

#### アクセント修飾型（aModType）

- **定義**: アクセントの修飾パターン
- **分布**: エントリの25%未満にしか非デフォルト値が付与されていない
- **値**: 6種類の非デフォルト値が存在

### G2P/TTSにおけるアクセント情報の活用

UniDicのアクセント情報はG2P/TTSパイプラインにおいて以下のように活用される：

1. **単語単位のアクセント**: aTypeから各単語のアクセント核位置を取得
2. **複合語のアクセント**: aConTypeを用いて複合語形成時のアクセント変化を計算
3. **韻律情報の生成**: アクセント情報を基に高低パターンを生成

### 制限事項

- UniDicのアクセント辞書は**複合語・固有名詞の網羅性が低い**
- 実用的なTTSシステムでは、辞書にない単語のアクセント推定が必要
- tdmelodicプロジェクトがこの問題に対処（ニューラルネットワークによるアクセント推定）

## 6. UniDicベースのG2Pアプローチ

### アーキテクチャ

```
入力テキスト
    ↓
[MeCab + UniDic] 形態素解析
    ↓
形態素列（品詞、読み、アクセント情報付き）
    ↓
[カタカナ→音素変換] pron/kanaフィールドを音素列に変換
    ↓
[アクセント処理] aType/aConTypeを用いて韻律情報を付与
    ↓
音素列 + アクセント情報
```

### 利点

1. **アクセント情報が辞書に内蔵**: IPADIC/NAIST-jdicでは別途アクセント辞書が必要だが、UniDicは辞書自体にアクセント情報を含む
2. **発音形フィールドの充実**: pron, pronBase, kana, kanaBase等の複数フィールドにより、正確な発音情報を取得可能
3. **語頭・語末変化情報**: iType/iForm, fType/fFormにより、連濁・音便等の音変化を辞書レベルで処理可能
4. **語種情報**: goshuフィールドにより和語・漢語・外来語を区別でき、読み規則の適用に活用可能
5. **階層的見出し構造**: 表記ゆれに対して一貫した解析結果を返す
6. **品詞体系の精緻さ**: 可能性に基づく品詞体系により、曖昧性の高い語の扱いが改善
7. **大規模な語彙**: IPADICより語彙のカバー率が高い

### 欠点

1. **辞書サイズが大きい**: 約133MBと、IPADIC（約50MB）やNAIST-jdic比で大きい。モバイル/Unity環境では問題になり得る
2. **短単位の問題**: 短単位は解析粒度が細かすぎる場合がある（例：「東京都」が「東京」+「都」に分割される）。G2Pでは適切に結合処理が必要
3. **OpenJTalkとの互換性がない**: OpenJTalkはnaist-jdic拡張フォーマット（フィールド14-15にアクセント情報）を使用しており、UniDicフォーマット（29フィールド）とは構造が異なる。NJD処理をそのまま適用できない
4. **複合語アクセントの課題**: aConTypeの仕様が複雑であり、OpenJTalkのC1-C5結合タイプとは異なるフォーマット
5. **NMeCabでの利用制約**: NMeCabはUniDicに対応しているが、`MeCabUniDic21Tagger`クラスが必要であり、IPADICモードとの互換性がない
6. **フィールドの欠損**: 全エントリに全フィールドが埋まっているわけではなく、`*`（該当なし）のフィールドが多い

### OpenJTalkアプローチ（naist-jdic）との比較

| 観点 | OpenJTalk (naist-jdic) | UniDicアプローチ |
|------|----------------------|-----------------|
| 辞書フォーマット | IPADIC + 2フィールド拡張 | UniDic 29フィールド |
| アクセント表現 | `核位置/モーラ数` + `C1-C5` | `aType` + `aConType` + `aModType` |
| NJD処理 | 既存実装あり（OpenJTalk/jpreprocess） | 独自に実装が必要 |
| 辞書サイズ | 比較的小さい | 大きい |
| 語彙カバー率 | 中程度 | 高い |
| 発音情報の詳細度 | 基本的 | 充実（出現形/基本形/仮名形） |

## 7. ライセンス

### ライセンス形態

UniDicは**トリプルライセンス**で提供されている：

| ライセンス | 概要 |
|-----------|------|
| **GPL v2.0** | コピーレフト。派生物もGPLで公開する必要がある |
| **LGPL v2.1** | 弱いコピーレフト。ライブラリとしてのリンクは自由 |
| **修正BSD** | 最も許容的。著作権表示と免責事項の記載のみ必要 |

利用者はこの3つのライセンスから選択（または組み合わせ）して使用できる。

### 追加条件

UniDicを使用した研究等の成果を公表する場合は、UniDicを使用した旨を明記することが求められている。

### Creative Commonsライセンス

一部のUniDic製品では **CC BY-NC-SA**（表示-非営利-継承）ライセンスも選択肢として提供される場合がある。この場合、商用利用は原則禁止（例外申請は可能）。

### 本プロジェクト（C#/.NET G2P）への影響

- **BSD選択時**: 最も自由度が高く、商用利用・プロプライエタリ製品への組み込みが可能
- **LGPL選択時**: ライブラリとして使用する限り、アプリケーション本体のソース公開は不要
- **GPL選択時**: 派生物全体をGPLで公開する必要があり、プロプライエタリ利用には不向き

**結論**: BSDライセンスを選択すれば、本プロジェクトの目的（Unity対応ライブラリ）に最も適合する。

## 8. SudachiPy/Sudachiとの関係

### Sudachiの概要

Sudachiは株式会社ワークスアプリケーションズ徳島人工知能NLP研究所が開発したJava実装の日本語形態素解析器である。Python版のSudachiPyも提供されている。

### SudachiDictとUniDicの関係

SudachiDictは以下のようにUniDicと深く関連している：

1. **UniDicベースの品詞体系**: SudachiDictはUniDicの品詞体系を採用している
2. **ユーザー辞書のID体系**: ユーザー辞書作成時のleft-idはunidic-mecab 2.1.2を参照
3. **短単位との対応**: SudachiのMode A（最小分割）はUniDicの短単位に相当

### SudachiDictの辞書バリエーション

| 辞書 | 内容 | 語彙数 |
|------|------|--------|
| **Small** | UniDicの語彙のみ | 最小 |
| **Core** | 基本語彙（デフォルト） | 中程度 |
| **Full** | 各種固有名詞を含む | 最大 |

### G2Pへの応用可能性

SudachiはUniDicベースの品詞体系を持つが、以下の点でG2P直接利用には課題がある：

- **読み情報**: Sudachiは読み情報を提供するが、UniDicのような詳細な発音形フィールドは持たない
- **アクセント情報**: SudachiDictにはアクセント情報が含まれていない
- **Java/Python依存**: SudachiはJava実装、SudachiPyはPython実装であり、C#/.NETからの直接利用は困難

## 9. 本プロジェクトへの示唆

### UniDicをG2P辞書として採用する場合の検討事項

#### 採用する場合のメリット
- アクセント情報が辞書に統合されており、別途アクセント辞書を用意する必要がない
- 発音形・語頭/語末変化情報が充実しており、正確な音素変換が可能
- BSDライセンスで利用可能
- NMeCabが既にUniDicフォーマットに対応済み

#### 採用する場合の課題
- OpenJTalkのNJD処理パイプラインとの互換性がなく、NJD処理を独自に再設計する必要がある
- 辞書サイズが大きく、Unity環境ではアセットサイズが問題になる可能性がある
- アクセント結合規則のフォーマットがOpenJTalkのC1-C5とは異なり、変換またはマッピングが必要

#### 推奨アプローチ

**Option A: naist-jdic拡張フォーマットを維持（推奨）**
- OpenJTalk/jpreprocessの既存NJD処理実装を活用できる
- 既存のエコシステムとの互換性が保たれる
- 辞書サイズが小さい

**Option B: UniDicを採用し独自パイプラインを構築**
- より正確な発音・アクセント情報が利用可能
- 将来的な拡張性が高い
- ただし実装コストが大幅に増加する

**Option C: ハイブリッドアプローチ**
- 基本はnaist-jdic拡張フォーマットを使用
- UniDicのアクセント情報を補助的に参照
- OpenJTalkのmecab-naist-jdicが実際にunidic-csj.csvとnaist-jdic.csvの両方から生成されている点を活用

### tdmelodicとの連携可能性

tdmelodic（PKSHA Technology Research）は、UniDicの語彙に対してニューラルネットワークでアクセントを推定するツールである。UniDicに登録されていない複合語・固有名詞のアクセント推定に有用であり、将来的にC#への移植も検討に値する。
